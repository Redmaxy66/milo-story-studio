| 2026-08-30 | D-008 | Use tagged canon releases for immutable canon provenance | Repo HEAD moves for workflow and documentation changes, so it is not a reliable canon identity. Explicit tags such as `canon-v1.0` represent intentional approved canon releases and resolve to immutable commit SHAs. | A canon release comprises the five authoritative Character Bible files plus `03-prompts/MILO_CANON_CONTEXT.md` and `02-story-system/CONTINUITY_RULES.md`. `canonVersion` stores the human-readable tag (for example `canon-v1.0`); `canonRef` stores the immutable full commit SHA resolved from that tag. Generated Concepts, Outlines, Scripts and later production artifacts must retain both fields. Downstream review and production must use the stored `canonRef`, never repository HEAD. Canon tags are created only for meaningful approved canon changes after the two derived runtime files have been reconciled with the five authoritative source files. |
| 2026-08-30 | D-009 | Freeze canon provenance for the full story lineage | Allowing later stages to adopt a newer canon release would make one story internally inconsistent and continuity review non-reproducible. | Concept Generation assigns the story's `canonVersion` and `canonRef`; Outline, Script, Continuity Review, and later Production Package stages inherit those values unchanged. Migration to newer canon must be explicit, never automatic mid-lineage. |
| 2026-08-30 | D-010 | Make the Stories row the authoritative canon-lineage record | The story itself should answer which canon governs all of its downstream artifacts without traversing Concepts, Outlines, or Scripts. | `Stories.canonVersion` and `Stories.canonRef` are the source of truth. Concepts, Outlines, Scripts, continuity outputs, and production packages must match the Story record. Any mismatch is a deterministic validation failure. |
| 2026-08-31 | D-011 | `Milo Failure Handler v0.1` may remain Published as an explicitly approved handler-specific operational exception. Publication is not technically required by n8n, and this exception does not create a general permission to publish other Milo production workflows. Any future change to the Failure Handler publication state remains a separately authorised production action. | Read-only assessment established that the handler's Error Workflow and sub-workflow roles do not require publication, the workflow has no webhook, schedule, or equivalent externally initiated production trigger, and the current technical risk is low. | The handler may remain Published without changing Milo's default protection for all other production workflows. Its live publication state must not be changed without separate production authority. |
| 2026-08-31 | D-012 | Records created before formal canon provenance that have blank `canonVersion`/`canonRef` are classified as PRE-CANON LEGACY records. Blank lineage must never be interpreted as `canon-v1.0` or any other canon release. Pre-canon lineages may remain as historical records but are not eligible to progress into M7 or later production stages unless a separately authorised migration establishes valid lineage for the complete Story lineage. Migration must never fabricate provenance. Archival or deletion remains a separate record-specific decision. | Five Stories, fourteen Concepts, and two Outlines pre-date formal canon provenance and have blank lineage; their original runtime canon cannot be established reliably, so retrospective assignment would create unproven provenance. | Pre-canon records remain historical and ineligible for M7 or later production by default. Any migration, archival, or deletion requires separate authority and must preserve provenance integrity. |
| 2026-09-01 | D-013 | Production Packages are immutable, append-versioned production blueprints. Each package preserves authoritative Story canon lineage, upstream artifact provenance, and generation provenance. Package scene content is persisted as immutable child scene records. The package's asset manifest defines planned assets only; realised media and its provenance must be stored separately and linked by `packageId` and `assetId`. M7 does not itself render external media or perform publishing. | M7 needs reproducible production instructions without mutating historical package intent when later renders, providers, prompts, or package generations change. Separating immutable package intent from downstream realised-asset provenance preserves auditability while keeping M7 within its approved production-preparation boundary. | M7 uses version-specific `MILO-###-S01-P##` package IDs, one immutable `Production Packages` header row plus immutable `Production Package Scenes` child rows, deterministic generation/supersession provenance, and stable planned `assetId` values that M8 or later can reference from a separate realised-asset store. |
| 2026-09-01 | D-014 | New Stories created after governed canon provenance carry an explicit Story-level canon-initialisation state. Only Stories explicitly marked `PENDING` by Story Intake may receive first canon assignment from Concept Generation. Historical blank-lineage records without that marker remain PRE-CANON LEGACY under D-012. Successful first assignment changes the marker to `ASSIGNED`. Existing valid canon lineage is never automatically replaced. The marker controls eligibility for first assignment of blank lineage; absence of the marker does not invalidate a Story that already carries valid governed `canonVersion`/`canonRef`. | Blank canon lineage alone cannot distinguish a newly created Story awaiting its first governed canon assignment from historical PRE-CANON LEGACY records. An explicit provenance-state marker provides a deterministic boundary without relying on Story IDs, timestamps, row position, or other heuristics. | `Story Intake` is the only normal workflow that creates `canonInitializationState=PENDING`. `Concept Generator` is the only normal workflow that transitions `PENDING` to `ASSIGNED` during first governed canon assignment or recovery of a partial assignment. Blank-marker historical rows are never automatically initialised, while already-valid governed lineage remains usable even when the marker is absent. |
